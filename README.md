# Чаевые — HotelTips (Android, Kotlin, Jetpack Compose)

Роли: **администратор**, **гость**, **сотрудник**. Данные хранятся локально в зашифрованной БД.

## Запуск
Android Studio Ladybug+, JDK 17, проект — в папке с **латинским путём** (например `C:\Projects\HotelTips`).

**Debug-сборка** создаёт демо-данные (подсказка на экране входа):
`admin / Admin123!x`, сотрудник во Вьетнаме `man / Man12345!x` (₫), сотрудник в Таиланде
`somchai / Somchai123!` (฿), гости `anna / Anna12345!` (комн. 410) и `emma / Emma12345!` (комн. 120).
Названия демо-отелей вымышленные и помечены «(demo)».

**Release-сборка** не содержит ни демо-данных, ни паролей: при первом запуске приложение
просит создать администратора. Пароли и подсказки вынесены в `src/debug` и в APK не попадают.

## Языки, страны, города, отели
- **Язык интерфейса:** русский, английский, японский, китайский. Переключается флагом в шапке
  на любом экране (и на экране входа) — приложение мгновенно перезагружает тексты, введённые данные не теряются.
  Все тексты лежат в `res/values*/strings.xml`; первый запуск берёт язык телефона.
- **Справочник:** Вьетнам, Таиланд, Лаос, Камбоджа, Мьянма, Малайзия, Сингапур, Индонезия, Филиппины, Бруней
  с городами и названиями на 4 языках — файл `domain/model/Geo.kt` (новые страны и города добавляются там).
- **Отели** хранятся в БД: администратор добавляет их во вкладке «Отели». Сотрудники и гости привязаны к отелю,
  комнаты уникальны в пределах отеля.
- **Регистрация гостя** — пять шагов с анимацией: язык → страна → город → отель → данные.
  Показываются только страны и города, где уже подключены отели; единственный город выбирается сам.
- **Валюта** определяется страной отеля (VND, THB, LAK, KHR, MMK, MYR, SGD, IDR, PHP, BND): свои быстрые суммы
  и лимиты (`Currency` в `Geo.kt`, значения ориентировочные), суммы разных валют не складываются.
- **Перевод сообщений гостей** (ML Kit, на устройстве) — на язык интерфейса читающего.

## Безопасность

| Угроза | Защита |
|---|---|
| Кража файла БД | БД шифруется SQLCipher (AES-256). Ключ случайный, хранится зашифрованным ключом из Android Keystore (user authentication, окно 120 с) — вне приложения прочитать нельзя |
| Подбор паролей по базе | Пароли не хранятся и не шифруются, а **хешируются**: PBKDF2-HMAC-SHA256, 310 000 итераций, своя соль + «перец» (HMAC с ключом Keystore). Обратной операции не существует — пароль не видит никто, включая администратора |
| Подбор паролей в приложении | 5 ошибок подряд — блокировка входа на 15 мин, одинаковое сообщение и время ответа для несуществующих логинов, сравнение за постоянное время |
| Слабые пароли | Не короче 10 символов: заглавная, строчная, цифра и спецсимвол, не равен логину, не из списка частых |
| Подмена сессии | Сессия зашифрована (AES-GCM, Keystore), живёт 12 часов, роль всегда перечитывается из БД |
| Доступ к чужим данным | `AccessGuard`: каждая операция в репозиториях проверяет роль и владельца. Администратор — сотрудники и их данные; сотрудник — только свои; гость — только свой номер |
| Смена данных | Пароль сотрудника сбрасывает только администратор (старый пароль он не видит); свой пароль меняет сам пользователь, зная старый |
| Кража денег | Вывод — только владелец счёта и **только после повторного ввода пароля**; подпись HMAC на каждой записи о чаевых и выводах: изменённые в обход приложения записи не учитываются, вывод блокируется |
| Потеря денег сотрудника | Нельзя удалить сотрудника с невыведенным остатком |
| Мошенничество гостей | Лимиты: 10 платежей в час, 10 000 000 ₫ в сутки; подтверждение суммы; платёж только сотруднику своей комнаты |
| Утечки с экрана | В release запрещены скриншоты и превью в списке недавних |
| Утечки через ОС | Бэкапы выключены, открытый HTTP запрещён |
| Анализ APK | R8-обфускация в release; секретов и демо-паролей в коде нет |
| Расследование | Журнал аудита (`audit_log`): входы, блокировки, смены паролей, платежи, выводы — без секретов |

## Обновление с прошлой версии
Схема БД изменилась (добавлены отели): версия 2. Данные тестовой версии 1 при первом запуске
пересоздаются (в debug подставляются демо-данные). После выхода в продакшн схему нужно менять
только через `Migration`.

## Ограничения (важно)
- Администратор один на всю систему: видит все отели. Раздельные администраторы по отелям — следующий шаг.
- Курсы валют не используются; лимиты в разных валютах заданы вручную.
- **Деньги.** Подключён только локальный `SimulatedPaymentGateway`: реальные платежи не выполняются,
  банковские реквизиты не собираются. Успешный тест создаёт демо-запись чаевых в локальной БД.
  Для реальных денег потребуется сервер, который проверяет пользователя и права, подтверждает
  статус у провайдера и ведёт баланс. Подробности и сценарии тестирования — в
  `docs/payment-simulation-ru.md`; перед production симулятор и выбор тестового результата нужно убрать.
- На устройстве с root и инструментами вроде Frida опытный злоумышленник может обойти клиентские проверки.
- Данные локальные: у каждого телефона своя база.
- Журнал аудита пока без экрана просмотра.
- Сессия не завершается по бездействию (только по истечении 12 часов).

## Вход гостя по QR-коду комнаты

На экране входа появилась кнопка **«Войти по QR-коду комнаты»**. Сканирование открывает встроенный интерфейс Google Play services для QR-кодов. После распознавания пользователь видит отель и номер, имя **«Гость»** (переводится вместе с языком интерфейса) и может заменить имя перед входом.

### Формат QR

QR должен кодировать **ID отеля и номер комнаты**. Поддерживаемый рекомендуемый формат:

`hoteltips://guest?hotelId=12&room=410`

Для проверки на **чистой debug-сборке** в демо-данных первый отель обычно имеет ID `1`, а комната `410` назначена сотруднику. Пример тестового значения QR: `hoteltips://guest?hotelId=1&room=410`. Для теста в репозитории приложен готовый QR `docs/demo-room-410.png`; его можно открыть на мониторе/другом устройстве и отсканировать кнопкой приложения. Собственные коды генерируйте в таком же формате.

Также принимаются HTTPS-ссылки с query-параметрами `hotelId` и `room`, строка `hotel_id=12&room_number=410` и JSON `{"hotelId":12,"roomNumber":410}`. Одного номера комнаты недостаточно: номера могут совпадать в разных отелях. Значение `hotelId` — внутренний числовой ID отеля из базы приложения, а не название отеля.

Перед созданием гостевой сессии приложение проверяет, что отель существует и на номер назначен сотрудник. Для одной установки приложения используется стабильный анонимный ключ для пары «отель + номер», поэтому повторное сканирование того же QR обновляет имя гостя, а не создаёт новую запись каждый раз. Пароль для QR-учётной записи генерируется случайным и не показывается пользователю; вход через обычную форму по этому паролю не предполагается.

### Ограничения безопасности прототипа

Сканирование QR — это **гостевой доступ к комнате, а не проверка личности**. Поскольку текущий проект хранит данные локально и не имеет серверной авторизации, текст QR теоретически можно скопировать или подделать. До реального запуска нужно перенести проверку на сервер и выдавать подписанный, отзываемый токен комнаты (без персональных данных и без секретов в самом QR). Проверка в приложении — полезная защита от ошибок, но не замена серверной авторизации.

**Ограничение текущей локальной версии:** отель и назначенный сотрудник должны уже присутствовать в зашифрованной БД именно на устройстве гостя. Например, debug-сборка заполняется демо-данными; на чистой release-установке этих данных нет, поэтому QR-вход не сможет подтвердить отель/комнату. Для размещённых в реальном отеле QR-кодов и передачи чаевых/обращений между разными телефонами требуется API-сервер и общая база данных; один локальный Room не синхронизирует устройства.

### Зависимость сканера

Используется Google Play services Code Scanner. На устройстве должны быть доступны и обновлены Google Play services; ручное разрешение камеры приложению не требуется, интерфейс сканирования предоставляет сервис Google. Устройства без Google Play services потребуют отдельной встроенной реализации на CameraX.


## Payment simulation (no provider connected)

The guest tip flow currently uses `SimulatedPaymentGateway` only. It makes no network requests, collects no card/bank credentials, and does not charge or transfer real money. The UI labels the flow as a simulation and shows a `SIM-...` reference for each attempt.

### Tourist market demo profiles

- Russia: Mir and SBP demo options.
- China: Alipay, WeChat Pay, and UnionPay demo options.
- Italy: Visa/Mastercard bank-card, PayPal, and Apple Pay/Google Pay demo options.
- United States: Visa/Mastercard bank-card, PayPal, and Apple Pay/Google Pay demo options.

These lists are demo scenarios only, not a promise that a future acquirer supports a method or market. The selected tourist market chooses a UI/payment-method profile; it does **not** change the tip currency. The amount remains in the hotel's configured currency (for example VND or THB). No fake exchange rate is applied.

### Test outcomes

The guest can select `Approved`, `Declined`, or `Cancelled` to exercise the result paths. Only an approved simulation creates a demo tip entry. A declined/cancelled attempt does not add a tip. Do not enter card numbers, CVV, passwords, bank credentials, or real wallet authorization details anywhere in the simulation.

### When a real provider API is available

Keep `PaymentGateway` as the domain port and replace the `SimulatedPaymentGateway` binding in `AppContainer` only as a deliberate integration change. A real payment adapter should use provider-hosted checkout/SDK or tokenized payment data, server-side secrets and a server-verified webhook. Do not move API secrets into the Android app. Before live capture is enabled, implement an idempotent payment-intent state machine and reconciliation/compensation for the boundary between payment status and the local tip ledger; the current local simulator does not solve distributed transaction consistency.

Automated unit tests for the demo gateway live in `app/src/test/java/com/hoteltips/data/payment/SimulatedPaymentGatewayTest.kt`.
